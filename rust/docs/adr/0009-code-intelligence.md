# ADR 0009: Code intelligence and transactional builds (RUST-05)

Status: accepted

## Code intelligence

- `ragmonk-code` ports `code/{parser,extractor,resolver,framework_rules,processor,graph}.py`.
  It uses the reference's `.scm` queries verbatim, with one exception. The
  crates.io Python grammar keeps the `(expression_statement)` wrapper that the
  reference's bundled grammar inlines, so the class-field pattern matches one
  level deeper and captures the same nodes. A test pins every query file to
  the reference while the Python tree exists.
- Grammars: `tree-sitter` 0.25 with the official grammar crates (C#, Go,
  Java, JavaScript, Python, Rust, TypeScript/TSX). The grammars are C code
  compiled by `cc`; the project itself still has no `unsafe`.
- Compatibility evidence: `compat/golden/code.json` is generated by the
  Python reference over `compat/fixtures/code`. That corpus covers 8 grammars,
  overloads, decorators/attributes, routes, impl/receiver methods,
  cross-file references, a syntax error and an unsupported extension.
  Entities (kind, name, qualified name, parent, signature, full range) and
  relationships (type, endpoints, symbol, resolver, confidence, location,
  evidence) must match exactly. They match both for the pure pipeline and
  end to end through the indexer.
- Identity: entity IDs are `v2::entity_id(file_id, kind, qualified_name,
  ordinal)`. Relationship IDs are `v2::relationship_id(source, type,
  reference text or target, ordinal)`. Both are stable across rebuilds
  (tested by wiping all V2 state and rebuilding).
- Parse failures: a tree with syntax errors fails only that file,
  permanently, with `parse_error`, like the reference's `CodeParseError`.
  Unsupported code extensions are indexed with no entities.
- Source locations are `<relative path>:<line>`, not absolute paths, so the
  knowledge store is portable.

## Whole-build resolution (V2 quality change)

The reference resolves cross-file references at publish time against
whatever files happened to be indexed earlier in the same run. The outcome
therefore depends on processing order, and is never revisited when a target
appears or disappears later.

V2 changes this:

1. Workers resolve only same-file references.
2. Other references are stored as `pending`, with their raw
   `reference_text` (knowledge migration v3).
3. A `BuildFinalizer` (`CrossFileResolver`) re-resolves every cross-file
   reference against the complete build before it becomes visible. This
   includes unchanged files, so a newly added definition resolves old
   callers, and a deleted one leaves no dangling edges.

The resolution rules and tie-breaks are the reference's. On the fixture
corpus the result equals the reference resolved against the whole corpus.

## Transactional builds (storage/indexing change)

Two changes made by this phase replace RUST-04's write strategy:

- **One transaction per build.** Each build runs inside one SQLite
  transaction, a "session".
  - A full rebuild writes a new build next to the visible one, commits it
    while it is still invisible (the control plane points at the old build),
    then publishes and garbage-collects.
  - An incremental pass updates the active build in place. Readers keep the
    last committed state until COMMIT; any failure or crash rolls the whole
    pass back.
  - Nested writes use savepoints. Leftover `building` builds from a crash
    between commit and publish are garbage-collected.
  - Measured on 3,001 C# files: cold indexing went from 16.4 s to 4.2 s,
    because each page is written about once instead of once per batch. A
    single edit went from 3.5 s to about 0.35 s, because it no longer copies
    the whole build (`carry_forward_except` is kept, but the coordinator no
    longer uses it).
- **FTS rows share their base row's rowid** (migration v3 re-keys existing
  rows with their content intact). Per-file and per-build deletes are now
  rowid lookups instead of full FTS scans, which had made indexing
  quadratic.
- The writer batches up to 64 already-prepared files per write, and hot
  statements use the prepared-statement cache.

## Benchmarks

`compat/benchmarks/rust-code-csharp-{300,3000}.json` hold the Rust results;
`python-code-csharp-3000.json` holds the reference on identical input.

| Scenario | Rust | Python CLI |
|---|---|---|
| Cold | ≈4–5 s | 52 s |
| Single edit | ≈0.35 s | 2.7 s |
| Warm, no change | 0.06 s | 1.7 s |

Most of an incremental pass is now whole-build resolution: about 0.25 s
over 82k relationships. Narrowing it to the affected symbols is a possible
later optimization.
